      MAKE A CORRECTION

      Describe one repair. WAKE prepares the candidate.

      1. Open the correction workflow. Sign in to GitHub with permission to run this repository’s workflows. Choose Run workflow on master.
      2. Describe the problem and expected behavior. In request, explain one concrete repair. In paths, list one to four existing files separated by commas. This first capability covers wake/assets/*.js, *.css, *.html and docs/*.md.
      3. Run it. WAKE sends only that request and those selected source files to Gemini. It validates the returned edits, runs checks in a separate container with no credentials or network, then opens a draft pull request if checks pass.
      4. Review the result. Open the draft’s diff and linked run. Check the behavior and limitations. Merge an acceptable change through GitHub; publish the website through its normal release process. Failed runs keep their logs and any proposal artifact.

      THE CHANGE BOUNDARY

      What can change, and what cannot

      The source workflow can write a bounded review branch. It cannot edit the kernel, governance, authority records, provider credentials, dependencies, tests, deployment bindings or this workflow. Its evaluator is installed code, outside the model’s edit allowance.

      The native policy lane can change only its installed context-selector setting after its own evidence checks. Neither lane can erase earlier receipts, count its own changes as research progress, change spending limits or grant itself broader permission.

      Review does not require you to copy code by hand: the proposed files are already on the draft branch. Broader runtime self-modification needs a separately versioned capability and compatible runtime release.
